# Atyaf — project contract and implementation notes

Atyaf is a Linux Desktop application for managing multiple independent profiles of a single executable, including portable applications extracted into a managed library. The application ID is `com.h.atyaf`, retained from the existing Linux CMake configuration. Unspecified language and interaction options resolve to Arabic/English and automatic contextual Split View respectively. The contract's `/dist` is interpreted as repository-root `dist/`, not a privileged filesystem-root directory. There is no AI component.

## Mandatory rules for every agent session

Every modification or new feature must be implemented in `lib/screens/desktop/` and its associated Linux integration. Do not finish a session until both are checked. Linux is the only target; x64 and ARM64 are the supported architectures. All user-facing application strings originate in ARB, including errors, settings and developer headings. Developer identity values are the explicit exception in `core/constants/developer_info.dart`. User-entered names, paths, process output and technical error details are data, not UI labels. All UI colors belong to `core/theme`; do not introduce fixed text or colors into widgets. Read existing files before editing, run analysis and tests, and re-read the attached execution contract before finishing.

## Structure

- `core/theme`: exact requested light/dark palettes, one lavender accent derived from the layered application icon, surface borders of white 8% / black 6%.
- `core/l10n`: ARB and `flutter gen-l10n` generated delegates, automatic RTL/LTR; unsupported system languages fall back to English. `tool/generate_l10n.sh` runs the official generator and removes unrelated platform documentation from its boilerplate header. Both distribution scripts apply the same documentation-only normalization; generated localization behavior is unchanged.
- `shared/models`: applications, profiles and executable inspection records.
- `shared/services`: repository, runtime and process interfaces used across features; process services are shared by launcher, home and backup integrations.
- `shared/widgets`: bounded desktop content and scrollable dialog surfaces.
- `features`: actual application/profile CRUD, onboarding progress, preferences, contextual library state, approval and launch coordination, process/archives/desktop entry/backup contracts, safe log reading. Feature-specific interfaces stay within their own feature. Process lifecycle journaling lives in `features/process_manager/services/process_journal.dart` while concrete signaling/stream integration remains in `platform/linux`.
- `features/managed_storage` and `features/updates`: managed import commits and manually requested update coordination. Their shared staged-source/storage contract lives in `shared/services/managed_storage_service.dart` because both features consume it. No remote checker, network API or update timer exists.
- `platform/linux`: concrete SQLite, XDG filesystem, process, archive, managed storage/swap, Flatpak host bridge, desktop entry and backup integrations only; no abstract classes.
- `screens/desktop`: all actual screens, including contextual editors and launch history. `LayoutBuilder`, `Expanded`, `Flexible` and `Wrap` provide bounded layout. The central content is capped at 1240 pixels. Profiles use a full-width list rather than an uneven card grid.

## Storage and isolation

The managed root is `$XDG_DATA_HOME/com.h.atyaf`, defaulting to `~/.local/share/com.h.atyaf`. Invalid relative XDG roots are ignored. SQLite stores applications, profiles and launch history with parameter binding, WAL and a busy timeout; runtime directories and locks are private. Preferences persist language, theme and `onboarding_done` with shared_preferences, including accepted system-language/system-theme defaults when onboarding finishes. The existing Linux ID is used consistently in manifests and profile shortcuts.

Each profile has independently configurable config/data/cache/state/temp paths, arguments, environment and working directory. Default config/data/cache/state paths live below its managed profile directory. The default temporary path is a short private `/tmp/atyaf-<uid>/<UUID-v5(root/profile-id)>` directory so Electron/Chromium Unix socket names fit Linux's 108-byte pathname limit; explicit temporary paths and TMPDIR overrides are unchanged. HOME and XDG_RUNTIME_DIR retain the real host environment unless the user explicitly configures them. Environment is copied, never mutated globally. Argument and environment-value substitutions support `{config}`, `{data}`, `{cache}`, `{state}`, `{temp}`, `{home}` and `{profile}`. Users supply application-specific flags in a JSON string array, not a shell command. This is settings separation, **not a security sandbox**; applications that ignore XDG need their own flags. No executable launches on selection or extraction. Approval records an executable content fingerprint, owner and mode, and is invalidated when those change. Root, empty files, non-executables and setuid/setgid binaries are rejected.

Deletion is restricted to canonical descendants of the managed root; external programs and custom data paths are never deleted. Parent symlink escape checks apply even to link removal. Cross-session library locks serialize launching, deletion, export and restoration. A per-profile launch lock and process identity prevent duplicates. Native PID identity includes the boot ID and process start ticks to guard against PID reuse. Graceful termination waits up to five seconds; force kill is a separate confirmed action. Restart refuses to force kill implicitly. Window close requests graceful stop of running profiles and leaves the window open if any remain. Programs that daemonize independently may outlive their original tracked process; use foreground application flags when available.

Both complete output streams are continuously persisted asynchronously with per-chunk flush/backpressure, without silently discarding output. The UI labels its first-256-KiB preview, can open the complete canonically validated file using the Linux desktop handler, and can copy or stream-export complete reports to TXT without preview truncation. Clipboard reports above 64 MiB are explicitly refused with an export recommendation; TXT exports have no preview/clipboard size cap. Start/stop timestamps, PID, exit code and unexpected exit are persisted. An interrupted supervisor is reconciled explicitly rather than inventing an exit code. Logs and backups can contain secrets supplied by the user or printed by programs.

## Archives and backups

Python 3 is an intentional Linux runtime dependency; zstd is needed for `.tar.zst`. The native file picker uses XDG Desktop Portal's file chooser; native packages declare the portal and a compatible backend. Extraction uses Python tarfile without executing members. Absolute paths, `..`, special files, hard links, duplicate members and writes through archive symlink parents are rejected. Confined relative symlinks are deferred until all ordinary files have been extracted and their final chains are checked. Executable bits are preserved; privilege bits are stripped. A fresh private staging directory, 100,000-member cap and 8 GiB expanded-size limit bound extraction. Failed or canceled imports are removed. Candidate executables are displayed for explicit selection.

Backups contain a consistent SQLite snapshot, managed profiles and portable directories, not external applications or custom paths. External symlinks are rejected. Restore validates metadata, application/profile IDs, paths and environments, stages all data, resets approvals and uses rollback directories and a database transaction. Managed absolute paths are relocated if the XDG root changes. Stop all profiles before export or restore. UI preferences remain intact and old shortcuts are removed after restore; create new shortcuts from the restored profiles.

## Desktop integration and packaging

Profile `.desktop` files are placed in the host XDG applications directory (by default `~/.local/share/applications`). They invoke Atyaf with `--launch-profile ID`, never bypass profile settings. Exec quoting escapes reserved characters, percent codes and the desktop string layer. Profile icons go into XDG hicolor; desktop database refresh is optional if the utility is absent. StartupWMClass is configurable in the application editor.

The icon source, 1024 PNG, transparent safe-area foreground and background are in `assets/icon/`. `icons_launcher` is exactly 3.1.0 and configured for Linux only. Its Linux generator emits `snap/gui`; the unrelated generated snapcraft scaffold is removed, since the supported distribution commands are the two Linux scripts. Derived 64/128/512 icons satisfy Flatpak export constraints. Use `tool/generate_icons.sh` to keep the generated outputs consistent.

Flatpak uses GNOME 50 for GTK3/Flutter and system SQLite's versioned `libsqlite3.so.0`. Host filesystem access and `org.freedesktop.Flatpak` host-spawn permission are intentional: this application must manage and launch installed host executables. A Python host bridge starts child processes without a shell, reports the real PID/status, forwards both streams and validates identity before signaling its process group. Atyaf's managed library and shortcuts use the host XDG environment. File-picker `/run/host/` executable paths are translated back to host paths. Flatpak is not a restrictive sandbox for launched programs. AppImage shortcuts use the persistent AppImage path, not a temporary mount path.

Federated Flutter packages automatically resolve their upstream transitive plugin packages in pubspec.lock; only Linux plugins are registered/built. No other platform targets, integrations or build instructions are added.

## Update 1 — managed imports and manual replacement

**Application files are replaceable; Profile data is persistent.** Complete folder and archive imports now stage below `root/staging/<uuid>` and install below `root/applications/<application-id>/current`. Profiles retain their existing, physically separate `root/profiles/<profile-id>` layout. The SQLite JSON records gain the optional `executableRelative` field without a destructive migration. Existing managed `portable/<uuid>` applications remain supported and update in place, deriving their relative executable path on their first update. Existing folder references remain external until explicitly updated; no silent copy/migration occurs.

The application actions in `screens/desktop/home_screen.dart` expose Update in both languages. The user chooses a complete folder or archive, sees its name/path and the selected relative executable, and confirms replacement. Imports always show the discovered candidates with relative paths, sizes and permissions. Updates automatically reuse a valid saved relative path, otherwise require explicit selection. The application editor makes managed executable paths read-only so updates cannot accidentally switch managed applications to external files. The profile panel scrolls as a whole to accommodate the storage description at minimum window height.

`LinuxManagedStorage` reuses the private host Python archive helper for confined, bounded folder copies (including internal links, with absolute internal links relocated to relative links). Escaping/dangling links, special files, unreadable directories and recursive self-imports are rejected; executable permissions are retained and privilege bits stripped. Archive traversal protections remain unchanged. Staging directories and destination parents are checked for symlink aliases. Candidates are never executed during discovery/import/update.

The existing exclusive library lock serializes updates with launches, deletion, backup and restore. Running profiles are checked again inside the lock. The UI offers graceful stop, never implicit force kill, and refuses replacement while a profile remains running. Profile data paths and relevant environment overrides are checked lexically and canonically; a profile storing data inside replaceable application files blocks the update rather than losing data. Explicit arguments and working-directory settings remain unchanged.

Replacement renames the old directory to a private rollback location, renames the fully prepared directory into place, re-inspects the executable, then saves the single application record. Failure before commit restores the old directory automatically; rollback data is not erased if restoration itself fails. Successful updates remove the temporary old version. This is a same-filesystem, near-atomic exception-rollback mechanism, not a claim of power-loss transactionality across SQLite and filesystem renames. Profile records, approvals, data and shortcut files are not rewritten. Content-based launch approval still detects changed executable fingerprints. Shortcuts invoke stable profile IDs and therefore follow changed internal executable paths without regeneration.

Backups now include `applications` as well as legacy `portable` and `profiles`; restore swaps all three collections and preserves relative executable metadata. External-reference updates import a new managed copy without modifying/deleting the old external executable; the UI explains this distinction. Existing profiles are never recreated.

Reviewed Dart SDK Directory.rename documentation and Python standard-library copy/link behavior locally for this update. Online documentation fetches were unavailable during the session; the existing official references and local SDK/stdlib sources supplied the required filesystem API details.

## Diagnostics and short temporary paths — 1.1.0

The desktop Errors and diagnostics section collects persisted Atyaf failures and failed/interrupted profile launches. Home/settings/profile-save/window-close/report-action failures and Flutter/async uncaught exceptions are recorded with complete detail and stack traces in SQLite's additional `errors` table. Error journaling is best-effort if storage itself fails and retains console diagnostics. Existing backup restoration leaves the local Atyaf error journal intact rather than overwriting it. Old launch records remain readable; new records also save the executable used.

`ReportActions` is shared by errors and launch-history views. Complete-report copy and UTF-8 TXT export include localized metadata, stdout/stderr and optional system crash information. Export streams validated log files into a 0600 staging file inside a private 0700 sibling directory, then renames the file into place and removes the staging directory. Managed library destinations/aliases are rejected, and failed exports preserve existing destination files. Only previews are bounded. Reports can contain secrets; the UI warns before sharing. Errors and launches can be exported individually or together.

`LinuxCrashDiagnostics` uses optional host `coredumpctl info` on demand, never sudo or a raw core dump. Queries are constrained to the recorded PID, boot ID, start/stop interval, executable and current user's UID, reducing PID-reuse and unrelated-process disclosures. Missing tools/dumps/permissions are represented explicitly. Flatpak uses the existing host bridge. No network or automatic updater was added.

The reported Antigravity PID 632621 exited with SIGTRAP (-5); its actual stderr was `FATAL: ... Socket path too long: .../temp/scoped_dir.../SingletonSocket`. The cause was the old long per-profile TMPDIR, not evidence of a sandbox failure. Default temporary paths now use the short deterministic namespace above. Host Python uses directory-relative operations, owner/mode checks and O_NOFOLLOW: both parent and child must be real directories owned by the current UID with mode 0700. Deleting a profile removes only its deterministic default temporary directory; custom temporary paths/data remain untouched. Default temporary contents are transient and not exported in backups. Existing long managed temp directories are not destructively migrated. No `--no-sandbox`, privilege escalation or other insecure launch flags are inserted.

Local Linux unix(7) socket-path documentation, Flutter Clipboard SDK source, and native file-picker save-file API were reviewed. A real Antigravity startup with isolated test userdata and the new TMPDIR remained running for eight seconds and exited gracefully with code 0; this verifies the reported startup-path fix, not every IDE function.

## Account shortcuts and host browser integration

`HomeScreen` creates/refreshes a system application-menu shortcut on profile save and exposes a visible add-to-menu button for existing accounts. Names now contain only the profile name. `LinuxDesktopEntries` reads matching host desktop entries (canonical executable or explicit StartupWMClass) to reuse the application's icon; managed Electron resource icons are also discovered without executing candidates. Atyaf's icon remains the fallback when no original icon is found. Removing shortcuts and deleting profiles still remove their managed fallback icons. Existing shortcuts are not silently regenerated at startup; save the account or use its add-to-menu action to refresh it.

The native GTK runner suppresses first-frame window mapping for `--launch-profile ID`. `screens/desktop/shortcut_launch.dart` launches already-approved profiles without building the library UI and keeps a hidden supervisor alive until complete logs and exit status are persisted. Already-running profiles are not duplicated or stopped. Missing/stale approval and launch errors fall back to the normal desktop review/error UI; approval is never bypassed. This is direct access without opening the Atyaf window, not execution without the Atyaf supervisor.

`LinuxRuntime.prepare` writes a private per-profile `desktop-handlers/xdg-open` Python wrapper and a 0600 desktop-environment record. Its directory/script use mode 0700. The profile's PATH points to this wrapper and BROWSER uses `xdg-open` unless explicitly overridden by the user. The wrapper executes the host's real handler using the original HOME/XDG/desktop/session/locale environment, with an argument list rather than a shell. Profile environment secrets and unrelated host tokens are excluded. Profile XDG storage and application arguments remain isolated; browser selection and browser storage use the normal host settings. Flatpak-launched applications use the same host-side wrapper through the existing bridge. Handler records are refreshed on every launch, including after restoration. Applications using absolute handler paths, their own embedded browsers, or other opening mechanisms are outside this PATH-based integration. OAuth return handling and every Antigravity login flow are not claimed as verified.

Verification: all 74 Flutter tests, analysis, source-contract checks and the native x64 release build pass. New tests cover account names/icons/fallbacks, managed Electron icons, default-browser selection with the real system xdg-open despite conflicting profile MIME defaults, exact OAuth URL arguments, explicit overrides, secret exclusion, approval/changed executable handling, duplicate refusal, complete hidden-supervisor logs, and automatic shortcut save/rename in Arabic/English. A real release-binary X11 smoke launch with a separate temporary library persisted complete output and exit code 0 without mapping an Atyaf window. ## Shortcut icon repair

The reported white squares were reproduced as unresolved theme-name icons: the host hicolor index contains sizes through 512, not the previous 1024-only directory. The imported Antigravity IDE also stores its actual logo as `resources/app/resources/linux/code.png`, rather than a filename matching `antigravity-ide`.

`assets/linux/desktop_icon_helper.py` discovers local application logos (including nested Electron/VS Code `code.png`), resolves installed theme/pixmap references to actual files, validates full decoding through the existing GTK3 GdkPixbuf runtime, and atomically normalizes PNG/SVG/XPM images to a maximum 512px PNG. Input sizes and dimensions are bounded. No application candidate is executed and arbitrary extension/media icons are not recursively chosen. Corrupt or missing application images use the validated Atyaf fallback. The helper uses Python ctypes and existing host GTK3 libraries, without a new Python imaging package or external conversion executable; Linux initialization deploys the helper privately for native and Flatpak host use.

Profile icons now reside in host hicolor `512x512/apps`, and every generated desktop file uses its absolute icon path to avoid unsupported directories and theme-name cache lookup failures. Refreshing a shortcut removes its obsolete managed 1024 icon only after successful generation; deletion handles both old/new managed image paths. Original application icon files are never changed or deleted. The desktop shortcut actions now confirm that both shortcut and icon were refreshed through ARB-localized UI text.

All 77 Flutter tests, analysis, contract checks, Python compilation and the native x64 release build pass. Regression tests cover nested Antigravity logos, actual decoding and PNG dimensions/mode, SVG conversion, invalid PNG and absent theme references, legacy migration, original-file preservation and Arabic/English refresh actions. The two existing host shortcuts `hossam1` and `Hossam2` were repaired by changing only their Icon fields and installing normalized copies of the real Antigravity logo; names, Exec fields and account data were preserved. Original desktop files are backed up under `build/shortcut-icon-backups/`. GTK loaded both repaired icons successfully at 64×64 through GDesktopAppInfo and the normal icon lookup API. The installed executable and distribution packages were not replaced; future shortcut creation should use the updated release bundle until a new package is installed.
